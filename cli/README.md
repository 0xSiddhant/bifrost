# bifrost-cli

A command-line client for a [Bifrost](https://github.com/0xSiddhant/bifrost) LAN
hub that is already running. It pushes and pulls files, reads and writes the
shared clipboard, fetches saved documents, resolves go-links, reports server and
device state, and runs a LAN speed test — over the same HTTP API the browser app
uses, adding no server surface of its own.

## Install

The CLI is distributed as a tarball on the project's GitHub Releases, not on the
npm registry. `npm install -g` takes a URL directly:

```bash
npm install -g https://github.com/0xSiddhant/bifrost/releases/download/v<version>/bifrost-cli-<version>.tgz
```

The repository README's **CLI** section always names the current version's real
URL — it is regenerated by the release workflow, so it never goes stale.

A local tarball or a synced folder works the same way:

```bash
npm run build -w cli && npm pack -w cli
npm install -g ./bifrost-cli-<version>.tgz
```

On the machine that hosts the server there is nothing to do by hand: `npm run
build` and `npm run start` both re-install the global `bifrost` from whatever is
checked out (`scripts/cli-sync.ts`), so the command never drifts from the server
it talks to. `pm2 restart bifrost` does not trigger it — PM2 execs the server
directly.

After installing, `man bifrost` works too: npm links the packaged man page into
the system man path.

## Finding your bridge

By default the CLI talks to `http://bifrost.local:4646`. That name resolves
through your operating system's own mDNS support — the same route a browser
takes — which is dependable on macOS and depends on `nss-mdns` (Linux) or Bonjour
(Windows) elsewhere. When it does not resolve, every command says exactly that
and names the fix rather than printing a network error:

```
error: couldn't reach the Bifrost server at http://bifrost.local:4646 (ENOTFOUND) —
check it is running, or point the CLI at it with --host <address>
(or save one with `bifrost config set-host <address>`)
```

Three ways to point it somewhere else, in precedence order:

```bash
bifrost --host 192.168.1.20 status     # this invocation only
bifrost config set-host 192.168.1.20   # saved default for later invocations
                                       # otherwise: bifrost.local:4646
```

A bare host gets `http://` and port 4646; `10.0.0.5:8080` and full
`http://…` URLs are taken as written.

## Commands

Every command accepts the global flags `--host <address>` and `--json`.

### push — send files

```bash
bifrost push ~/Desktop/notes.pdf
bifrost push a.pdf b.jpg c.txt         # one request, not three
```

Files land in **Send**, the staging area, where any device can preview, rename,
delete or publish them. A batch is reported per file, so one rejected file (over
the size cap, a blocked extension) does not hide the ones that landed — and the
exit code says the batch was not wholly accepted. Uploads stream off disk: a
multi-gigabyte push does not grow the process.

### pull — list Downloads, or fetch from it

```bash
bifrost pull                                   # list files, folders and folder contents
bifrost pull notes.pdf                         # download into the current folder
bifrost pull Trip/notes.pdf --out /tmp/n.pdf   # a folder's copy, somewhere else
```

An exact path always wins, so `notes.pdf` means the one at the root even when a
folder holds one too. A bare name that matches files in two folders is reported
as ambiguous with both paths, rather than guessed at. The file is written as
`<name>.part` until the last byte arrives, and the CLI refuses to overwrite a
file that is already there.

### clip — the clipboard every device shares (Hermes)

```bash
bifrost clip "ssh pi@10.0.0.7"       # share text
bifrost clip                         # print the most recent entry
bifrost clip | pbcopy                # …the read half of the round trip
bifrost clip --list                  # every entry, with ids
bifrost clip --rm <id>               # delete one
bifrost clip "const x = 1" --code --lang ts --ttl 3600
```

### open — print a saved document

```bash
bifrost open my-config-a1b2c3                     # any kind, resolved for you
bifrost open my-config-a1b2c3 --type runestone    # skip the lookup
bifrost open trip-notes-a1b2c3 --out trip.md      # write it to a file
bifrost open my-config-a1b2c3 | jq .
```

A slug names a document but not which *kind*, so all four raw endpoints
(runestone, edda, groot, atlas) are asked at once and the one that answers is
used. A slug that somehow exists as two kinds is reported, and `--type` settles
it.

### preview — open a document's page in your browser

```bash
bifrost preview trip-notes-a1b2c3              # launches the browser
bifrost preview trip-notes-a1b2c3 --no-open    # just print the URL
```

Edda documents have a real rendered page (`/edda/preview/<slug>`). Runestone,
Groot and Atlas have none yet, so their raw content URL is opened instead —
which a browser renders readably — and the CLI says which of the two it did.
`--json` never launches a browser, whatever `--no-open` says.

### portkey and go — LAN go-links

```bash
bifrost portkey create router http://192.168.1.1 --note "the box"
bifrost portkey list -q router
bifrost portkey update router --url http://192.168.1.2
bifrost portkey rm router

bifrost go router          # print where it points
bifrost go router --open   # …and launch it
```

`bifrost.local/go/router` then works from any device. An unknown slug is
reported as not found rather than followed into the management page.

### status, devices — what the bridge says about itself

```bash
bifrost status     # profile, uptime, loaded modules
bifrost devices    # who has connected, and who is online (read-only)
```

### speed — LAN speed test

```bash
bifrost speed
bifrost speed --mb 25
```

Latency is the median of the server's configured number of round trips (never
the mean — one Wi-Fi retry would poison an average); the download clock starts
at the first byte, and the upload figure is the server's own timing. The result
joins the same history a browser-run test does. If another device is mid-test
the bridge says so and the CLI reports it plainly.

### config — the CLI's own settings

```bash
bifrost config show
bifrost config set-host 192.168.1.20
```

### update — install the latest published CLI

```bash
bifrost update
```

Resolves the latest GitHub Release's `bifrost-cli-*.tgz` and installs it. It
no-ops cleanly when the installed version already matches, and surfaces npm's own
output if the install fails.

### doctor — find the broken link before you trip over it

```bash
bifrost doctor
```

Walks the chain every other command runs through — config file, host resolution,
server reachability, server profile, CLI version, Node runtime — one ✓/✗/⚠ line
each, using the same remediation wording the failing command itself prints. The
version line is informational: a hub with no internet access still passes.

## Config file

`~/.config/bifrost/config.json` (`$XDG_CONFIG_HOME` is honoured; on Windows,
`%APPDATA%\bifrost`). It holds:

- `host` — the saved default from `bifrost config set-host`.
- `deviceId` — minted on first run and sent as `x-bifrost-device`, so clips,
  go-links and speed tests are attributed to this machine rather than left blank.
- `update` — the throttled cache of the last GitHub release check.

A missing or corrupt file falls back to defaults rather than failing a command.

## Network access

Only `bifrost update` and `bifrost doctor` reach the internet, and only to read
`https://api.github.com/repos/0xSiddhant/bifrost/releases/latest`, throttled to
one request every six hours across both. Every other command talks solely to the
bridge on your LAN. (The tradeoff of that throttle, stated plainly: a release
published minutes ago may be invisible to both for up to six hours.)

Nothing here touches an admin-gated route, so there is no PIN or login step —
the endpoints it uses are the same LAN-trust ones the browser app uses.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Success |
| 1 | A failure the CLI could name, including a partly-rejected push |
| 3 | The bridge could not be reached — the host did not resolve, or nothing answered |
| 4 | The bridge answered, and there is no such file, document or link |
| 5 | Something else holds the thing — a taken slug, a speed test in flight, an ambiguous slug |

## Output

`--json` puts machine-readable JSON on stdout and nothing else: progress goes to
stderr, errors go to stderr as `{"error":"…"}`, and no command launches a
browser. So `bifrost --json pull | jq '.[] | select(.type=="file")'` works
without filtering anything out first.
