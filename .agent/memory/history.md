- 2026-08-27 (later still) — **PLAN-22 follow-up: the two delays the owner reported, and what was actually behind them.** Both were reproduced before anything was changed. **(1) "Unlisted page navigation took too much time to show error page."** With the chunk request *hung* rather than refused, the panel never appeared at all — 45s and still counting, and because react-router keeps the previous UI while a route suspends, the click looked like it had simply done nothing. A refused connection fails instantly; a vanished host does not, and that is the commonest shape here. Fixed with an 8s `withChunkTimeout` around every route loader, every warm target (the pill could otherwise sit on *Warming…* indefinitely) and the offline-mode config read (a hung read left the toggle permanently disabled); `apiGet` gained an **opt-in** `timeoutMs` rather than a default, since Nimbus's transfers are long by design. Measured after: **45s+ → 8.4s**, and 0.1s when the device is properly offline and the browser fails fast on its own. **(2) The retry button I had shipped did nothing** — found by testing it rather than by report. Two layers cache the failure: `React.lazy` keeps a rejected payload for the life of the component (`lazyInitializer` re-invokes the loader only while the payload is uninitialised), and underneath it **the browser's module map records a failed URL as failed for the life of the document**. Probed directly in Chromium: a second `import()` of a previously-blocked URL produced *no network request at all*, while the same file under `?retry=1` — a different map entry — loaded fine. Vite owns the chunk URLs so cache-busting them from source is not available. The `lazy` payloads are now rebuildable (`app/lazyPages.tsx` + a `pageEpoch` in the shell, bumped only while a failure is on screen so nothing else is remounted), which genuinely recovers the case where the 8s timeout fired but the fetch landed a moment later; a hard failure can only be undone by a new document, so the panel offers **Try again** while the bridge is unreachable and **Reload the page** once it answers. **(3) Which of those two it shows is measured, not inferred** — the first version read `bifrostEvents.status` and live-verify caught it telling a freshly-offline user that the bridge was back and to reload, because an EventSource keeps reporting `open` for seconds after the network goes. The boundary now probes `GET /api/health` (3s) on each failure and every 5s while the panel is up, spending one free retry when the answer flips to up. **(4) "mDNS took too much time to reconnect."** Root-caused in `multicast-dns`: its 5s `update()` loop skips any address already in its `memberships` map — cleared only on `destroy()` — while the OS silently drops the group membership when an interface goes down. An interface that leaves and returns on the **same** address is therefore never re-joined: joined in bookkeeping, deaf in fact, until the process restarts. A new DHCP lease recovers by itself and an unchanged address never does, which is exactly why it read as intermittent. `watchNetworkChanges` now polls `lanIPv4Addresses()` every 5s and rebuilds the responder on any change, which also re-announces the service so other devices' caches refresh. Interfaces cannot be added or removed inside the test container, so `advertiseMdns` took two optional test-seam options and the whole loop is asserted: three advertisements as the address set drops and returns to the same value, and none after `stop()`. **Live-verified** on the built server: warm → offline → cold route answers in 0.1s with *Not available offline* and Try again → a warmed page still opens → back online and the panel switches **by itself** to *This page needs a reload* with the toast following suit; hung-chunk case answers in 8.4s; and the running server logged zero mdns rebuilds across ten minutes of polling on a stable network. 15 new tests; gate: lint / typecheck / 545 server + 830 client / build all green.
