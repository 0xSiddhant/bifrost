# Bifrost Architecture

One Node/Fastify process serves the static frontend, REST API, and SSE stream on one port. No separate backend service, no reverse proxy.

## The three modularization rules (non-negotiable)

1. **Vertical slices.** Code is organized feature-first: `src/modules/<feature>/` contains that feature's routes, usecases, services, and DB schema. Shared infrastructure lives in `src/core/` only.
2. **Modules never import each other. Only `core`.** Cross-feature communication goes through the core **event bus** (e.g. `bus.emit('file.uploaded', meta)`). Enforced by `eslint-plugin-boundaries` — a violating import is a build failure, not a style nit.
3. **A deployment manifest decides what loads.** `DEPLOY_PROFILE=local|cloud` selects which modules the composition root registers. `local` = everything. `cloud` (future) = internet-safe modules only (currently health, qr-tool, themes, heimdall, runestone, variant, edda, groot, atlas, loki, screensaver, client-logs, metrics, toolbox, offline-mode — see `MANIFEST` in `server/src/app.ts`), Postgres instead of SQLite, no mDNS. The server exposes `GET /api/capabilities`; the frontend renders nav/pages from it — one client build serves both profiles. The nav groups pages into **three category hub tabs** (Midgard = transfer, Ollivanders = dev tools, Diagon Alley = utilities); a tool with its own state and server module keeps its own route and is surfaced as a card on its hub, while Diagon Alley's pure-client tools have no route of their own and expand in place (PLAN-18). A category tab shows only when one of its modules is in the capabilities list.

## Layers inside every module

`route (HTTP concerns) → usecase (business rules) → service/repository (infrastructure)`.
Usecases depend on **repository interfaces**, never on Drizzle/fs/chokidar directly. Concrete implementations are injected by the module's `module.ts`. This is what makes the SQLite→Postgres swap mechanical later.

`screensaver` is **policy-only** (like `variant` is capability-only): it owns no rendering — the overlay is a client `features/screensaver/` canvas mounted at the app root, gated to desktop pointers and shown after an idle timeout. The module exists to serve/persist the Heimdall-tunable settings (`GET /api/screensaver/config` public, admin `PATCH /api/screensaver/settings`, `screensaver.settingsUpdated` → SSE for live rebind), mirroring the Loki settings pattern.

`variant` is **capability-only**: its `register()` is a deliberate no-op — all comparison runs client-side; the module exists purely so `/api/capabilities` advertises the page (and the Pensieve picker's runestone-capability check). Runestone shares the JSON stack (`core/json`, `core/ui/JsonEditor`, `core/ui/TreeView`) that Variant mounts twice — those live in client `core/` because features may never import features.

`toolbox` is capability-only on the same pattern (PLAN-18). Diagon Alley **is** the toolbox: thirteen pure-client tools open **in place** as a full-width panel at the end of the source card's row, rather than each owning a route. The mechanism is `core/ui/ExpandingGrid` (used-track-list column measurement + `ResizeObserver`, `panelInsertIndex`, a measured-or-hidden caret, the scroll plan, focus/Escape); `features/toolbox/` owns the registry and the bodies, which ship as **one** lazy chunk. Open state lives in the URL (`/diagon-alley/:toolId`), so Back closes the panel and a tool is linkable; an unknown or unsupported id renders the hub and **replaces** the URL. `/sigil` is a redirect to `/diagon-alley/qr` — the **`qr-tool` module is untouched**, since Midgard's Join card still reads `GET /api/qr/server-url`. A tool may declare `supported()`; its only user is SHA-256, because `crypto.subtle` is secure-context-only and therefore missing on every LAN device except the host Mac at `localhost` (UUID and the password generator use `getRandomValues`, which is not gated, so they work everywhere).

`offline-mode` is **policy-only**, the same shape as `screensaver`. The thing it enables is 100% client: a header switch on Ollivanders and Diagon Alley eagerly `import()`s the chunks for the six pure-client pages, so an already-open tab keeps working after the LAN drops (no Service Worker — those are secure-context-only and Bifrost is plain HTTP on the LAN, the same restriction that gates the SHA-256 tool). The module owns `GET /api/offline-mode/config` (public), an admin `PATCH /api/offline-mode/settings`, and `offlineMode.settingsUpdated` → SSE for live rebind, over one `settings` row (`offlineMode.disabledTargets`) — no new table. The registry is code-owned and travels as data because loaders cannot; the `id → import()` map lives in `client/src/app/offlineWarmLoad.ts` (the composition-root tier — `core/` may not import `features/`). A cold route opened with no bridge is caught by `client/src/core/ui/RouteBoundary` — one notification plus an inline panel, the shell and every warmed page left standing — rather than the app-wide `ErrorBoundary`'s crash card; anything that is not a missing chunk is re-thrown, so real bugs still reach it. Every route loader is bounded by an 8s `withChunkTimeout`, because a vanished host leaves the fetch hanging for the browser's own connect timeout rather than refusing it; and because a failed module URL is cached as failed for the life of the document, the panel offers a retry only while the bridge is unreachable and a **reload** once it answers again — which it decides by probing `/api/health`, not by the SSE status, which lags a network drop by seconds. Mechanism detail: [`docs/offline-mode.md`](../../docs/offline-mode.md).

## Core services (shared kernel — no feature imports)

`config` (zod-validated .env, overlaid with DB-stored runtime settings) · `reserved-roots` (the one list of the app's own URL path roots + `api`/`go`, guard-tested; Portkey slugs may not be one) · `db` (better-sqlite3 + Drizzle, WAL mode) · `logger` (pino → rotated JSON files with a file-count limit; the level is written as the **text** key `logLevel` (the numeric `level` stays beside it — pino's own multi-target transport worker routes on it, and dropping it silently drops every line); `moduleLogger` and `clientLogger` are **sibling** children of the root binding `source: 'server'|'client'` + `module`) · `event bus` (typed in-process emitter) · `sse-hub` (one SSE endpoint, all modules publish through the bus; carries per-connection metadata — deviceId/UA/IP — and an `onConnectionChange` subscription that presence consumes) · `auth` (`@fastify/secure-session` PIN sessions + revocable session epoch; decorates `app.requireAdmin`, which guards both Heimdall routes and theme write routes) · `mdns` (Bonjour advertisement, local profile only; a multicast send failure — the Wi-Fi it was advertising on going away — is a `warn`, never fatal, since bonjour-service's default error callback is `throw err` from a dgram send callback and used to exit the process over a network blip; and a 5s `watchNetworkChanges` poll rebuilds the responder whenever the LAN address set changes, because `multicast-dns` never re-joins an interface that returns on the *same* address — its `memberships` map is only cleared on `destroy()`, so the socket stays joined in bookkeeping and deaf in fact) · `http` (Fastify instance, static serving, error mapping) · `disk-usage` (the one recursive storage walk; Heimdall renders it, `metrics` samples it — synchronous by nature, which is why metrics keeps it on a slow cycle) · `backup` (`VACUUM INTO` a consistent DB snapshot + zip of `storage/` + `themes/`, online-safe; importable so PLAN-10's in-app button reuses it).

## Key data flows

- **Upload:** client `POST /api/files` (multipart) → busboy streams to `storage/tmp/` → usecase validates (size limit from config, filename sanitization, extension blocklist) → `link()` into `storage/uploads/` → `bus.emit('file.uploaded')` → recorded once, in audit-log's `audit_events` (PLAN-17b dropped the duplicate `upload_audit` table). Files written mode 0644, stored under the **sanitized name itself** — no timestamp prefix, with `-1`, `-2`, … appended only on a real collision (bounded at 50 attempts, then a short random suffix).

- **Staging (PLAN-17b — supersedes "uploads are write-only"):** `uploads/` is now a short-lived staging area its sender can act on: `GET /api/files/:name/preview` (metadata, served by `previews`) + `GET /api/files/:name/content` (bytes, with ranges), `PATCH /api/files/:name` (rename — a name the sanitizer would change is **422 with the clean name in `details.suggestion`**, never silently altered), `DELETE /api/files/:name`, and `POST /api/files/:name/publish` (move to `downloads/`). Every one resolves the name through `realpath` and proves it lands inside `uploads/`. Publishing is **`link()` then `unlink()`**, never `open(wx)` + `rename()`: `link` is an atomic no-overwrite reservation whose target already holds the complete bytes, so no window can strand a zero-byte file. The one window it leaves — a crash between the link and the unlink, leaving the file in both folders — is closed by a **boot sweep** that drops an upload sharing a `dev:ino` with a download. `EXDEV` (the folders can be configured onto different volumes) falls back to a fsynced copy through a dot-hidden staging file inside the destination. Publishing emits **`file.published` → SSE**, which owns the **banner only**: the Downloads *listing* still comes from chokidar's later `download.added`, and nothing may banner on that or every file announces itself twice. The payload carries `originDeviceId` so the sender's own devices stay quiet — a UX nicety, not isolation, and suppression happens **only when both ids are non-null and equal**. **This deliberately reverses the PLAN-02/05 decisions that `uploads/` has no read route and that admin sees metadata only** (see decisions.md, 2026-07-30).
- **Live download:** file dropped into `storage/downloads/` via Finder → chokidar (FSEvents, `awaitWriteFinish`, **`depth: 1`**) → `bus.emit('download.added')` → sse-hub broadcasts → every open client updates. Downloads served via controlled endpoint with path-traversal protection, never a raw directory listing.

- **Download folders (PLAN-24 — supersedes "the downloads watch is flat, depth 0"):** `downloads/` is **one level deep**. chokidar's own `depth: 1` is what enforces that — no application code counts path segments — so a file two levels down is silently never indexed rather than detected and rejected, and `addDir`/`unlinkDir` give folders their own rows. `DownloadEntry` carries `type: 'file' | 'folder'` and `parent`, and `GET /api/downloads` stays **one flat, SSE-synced array**: root files, folder rows and every folder's files together, which the client filters by `parent` for whichever of the two views is open. A folder's size and file count are **derived in the browser** from that same feed rather than pre-aggregated server-side, so the figure cannot drift from the rows it counts; ids hash the path *relative to* `downloads/`, which is what lets `previews` keep re-deriving them from its own independent scan (now one level deep too). `POST /api/files?folder=<name>` writes **straight into `downloads/<name>/`, skipping `uploads/` staging entirely** — the owner's "it will be default available for download", so there is no staging card and **no undo** — reusing the same tmp-file → `placeFile` hard-link → `chmod 0644` discipline every other write uses, so no new crash-safety mechanism exists: the worst a crash leaves is an *empty folder*, which is why no boot sweep was added for it. A `FolderPublisher` port (`FsFolderPublisher`) owns that, deliberately a third port rather than a graft onto `FileStorageRepository` ("uploads-side storage") or `UploadsStore` (whose methods all take a name already resident in `uploads/`). `mkdir` + a follow-up `stat` on `EEXIST` is what makes a folder name **append, never duplicate** — and settles the two-devices-race for free, since the loser's stat finds the directory the winner just made; only a name that is already a plain *file* is a conflict (409). Folder names are **silently sanitized and reported back** in `accepted[].folder` (the treatment a *filename* already gets, not the rename rule's 422 — mirroring the sanitizer into the client workspace to preview it is the drift this codebase avoids elsewhere), and the sender alone hears about it afterwards, once per batch. `file.published` gains an optional `folder`, so the banner names the destination and dedupes per folder rather than merging a folder wave with a concurrent plain Move.

- **Folder → zip:** `GET /api/downloads/:id/archive` streams a zip of one folder's files via **`archiver`** (`core/backup`'s `zip` CLI stays where it is — that one is a rare synchronous whole-process snapshot, this can be asked for by several devices at once). The layering is the point: `FsFolderArchiver` is the only place `archiver` and a filesystem path exist, `DownloadReader.confineFolder` does the realpath-prefix proof (the same one `confine()` already ran, asserting `isDirectory()`), and `ArchiveFolderUseCase` only ever hands the route a `{ stream, zipName }` pair — mirroring how `respondWithFile` stays fs-free. The entries are an **explicit per-file list, never `archive.directory()`**, so a two-levels-deep Finder addition the watcher never indexed cannot ride along; a file deleted mid-zip is a logged warning rather than a corrupt archive, an empty folder is a valid empty zip, and the response carries **no `content-length`** because a streamed zip's size is unknown until `finalize()`. A file id asking for `/archive` is a clean 400, and a folder id asking for `/content` an explicit 404 rather than an incidental one.
- **Pensieve (the one document library, PLAN-21):** there is **no server side to this at all**. `/pensieve` is a client shell that fans out with `Promise.allSettled` across the document kinds this profile serves — `runestone` (JSON), `edda` (Markdown) and, since PLAN-19, `groot` (YAML) — merges the results and sorts them in the browser. **Groot's arrival was the return on that design: one `LIBRARY_REGISTRY` element and no page change**, exactly as the fake-kind test had been pinning. A server endpoint returning "all documents" would have to read three modules' tables from one place, which **rule 2 forbids**; the only legal shapes would be a core-owned aggregate table or a bus-fed projection, and both couple storage that is deliberately uncoupled. `allSettled` rather than `all` is load-bearing: one module being down must degrade to "that kind couldn't be loaded · Retry" beside the kinds that answered, never to a blank page. Everything that decides *what* a kind is — label, capability, `list`, `remove`, editor route, icon, palette slot, SSE events — is one entry in **`client/src/core/library/`**, so **a fourth document type is one array element and no page change** (pinned by a test that registers a fake kind). The page itself lives in `app/pages/` because it is a shell across features and features may not import features; it owns no capability, rendering whenever at least one kind is present. The badge colour follows the **kind**, not the row position — a scoped exception to the positional-palette rule, on the Accio hostname-tile reasoning: a type must stay recognisable while the list is re-sorted under it. `pensieve` joined `RESERVED_ROOTS` when it stopped being a nested segment. **Scale bound, stated rather than discovered:** each kind returns its whole matching set (no `limit` is sent, so the server's own 200-row default applies), which is correct for a household tool holding tens to hundreds of documents; past thousands of rows the browser merge-sort is what breaks first, and the fix is a real merge cursor over the sorted streams, not a bigger fetch. Each row with a public raw-data URL also gets a **"Copy curl"** button beside its "API" link (`client/src/core/library/curl.ts`), built from a `mimeType` field paired with `apiRoute` on the registry entry — `curl -sS -H 'Accept: <mimeType>' '<origin><apiRoute>'`, verified against each kind's own route handler rather than assumed. A fourth kind that ships `apiRoute` picks the button up for free by also setting `mimeType`; the registry decides, the page doesn't change — the same promise the rest of this paragraph already keeps.

- **Runestone save:** editor `POST/PUT /api/runestone` → usecase validates (JSON parse, `RUNESTONE_MAX_DOC_KB` cap) → `runestones` table (id = 6-char handle anchoring the `<kebab-name>-<id>` slug; renames regenerate the slug, stale slugs 301) → `bus.emit('runestone.saved'|'runestone.deleted')` → SSE live-updates open libraries (the **Pensieve** page at `/pensieve?type=runestone`, one shell over every kind since PLAN-21); audit-log records both. Author stored as `author_device_id` only — names resolve client-side.
- **Runestone public data endpoint:** `GET /runestone/api/:slug` (outside `/api/`, wins over the SPA fallback) serves the **raw stored document text** as `application/json` with `Access-Control-Allow-Origin: *`, so a saved runestone doubles as a stable data URL for third-party tools. Stale slugs 301 to the canonical data URL; read-only — every write still goes through `/api/runestone`.
- **Edda (Markdown) save + share:** editor `POST/PUT /api/edda` → usecase validates only the `EDDA_MAX_DOC_KB` cap (markdown is free text — no content validation, an empty doc is valid) → `eddas` table (same id/slug/301 scheme as runestone) → `bus.emit('edda.saved'|'edda.deleted')` → SSE live-updates open libraries (the shared **Pensieve**, PLAN-21); audit-log records both. Three share surfaces: `/edda/<slug>` (editor SPA route, opens Preview mode on mobile), `/edda/preview/<slug>` (public rendered SPA page), and `GET /edda/api/<slug>` — the raw stored Markdown as `text/markdown; charset=utf-8`, CORS `*`, outside `/api/` (wins over the SPA fallback), stale slugs 301, `?download=1` → attachment. Reserved first segments (`preview`, `api`, `library`) are guarded in slug resolution. The Markdown renderer (`client/core/markdown/renderMarkdown` — marked GFM + highlight.js + heading ids + DOMPurify) is one pure function shared by **four** surfaces since PLAN-20: the live preview, the public page, the HTML/PDF export, and the file-preview modal.

- **Diagrams & print (PLAN-20, client-only — no module, route, table or capability):** a ` ```mermaid ` fence renders as a real diagram on every markdown surface, and an edda prints to PDF. **`renderMarkdown` stays pure and synchronous**: the fence emits a `<pre class="mermaid-src">` placeholder and a separate async pass (`core/markdown/mermaid.ts`, driven by the `useMermaidDiagrams` hook) swaps the SVG in — mermaid is async *and* needs a live DOM to measure text, so running it inside the renderer would break all four consumers at once. The pass lives in **core** rather than `features/edda/` because `features/previews/` renders markdown too and features may not import each other; `MarkdownViewer` therefore switched off its private `marked.parse` onto the shared renderer, gaining GFM, hljs and heading ids and closing a real drift. `import('mermaid')` sits behind the presence of a placeholder (pure `hasMermaid(md)` for the string path), so a fence-less document loads none of it. Diagrams are cached by source **and palette**, which is what makes typing cheap and a theme switch correct in one mechanism. Two properties are worth knowing because they were found the hard way: the pass **renders into the cache first and swaps synchronously last**, since the container belongs to React and a node captured before an `await` may already have been discarded; and every `dangerouslySetInnerHTML` consumer **must memoize its `{__html}` object**, because React compares that prop by identity and re-sets innerHTML on every re-render otherwise, erasing anything the pass just wrote. Untrusted input is the posture (any LAN device can save an edda; `/edda/preview/:slug` is public): `securityLevel: 'strict'`, `htmlLabels: false`, `suppressErrorRendering: true`, DOMPurify's SVG profile over the output, and mermaid's `secure` key list **extended** past its default to cover `themeCSS`/`theme`/`themeVariables`/`fontFamily` — the default leaves `themeCSS` writable by an in-document `%%{init}%%` directive, which is raw CSS landing in a `<style>` the sanitizer keeps, and was reproduced fetching an attacker URL. **PDF prints the generated export document in a hidden `srcdoc` iframe, never the app page**: the export template already *is* the clean document, so `.html` and `.pdf` are one artifact rather than a dozen `@media print` overrides hiding the shell, and the diagrams are inlined before the iframe exists, which removes the async race structurally. Cleanup is `afterprint` **plus a timeout fallback**. Each diagram is inlined into the export **twice** — the active theme for screen, ink-on-paper for print, toggled by `@media print` — because mermaid bakes colour into the SVG at render time and one copy cannot serve both.

- **Groot (YAML) save + advisories:** editor `POST/PUT /api/groot` → usecase validates only the `GROOT_MAX_DOC_KB` cap → `groot_docs` table (module name + generic noun, the `accio_links` precedent — `runestones`/`eddas` does not generalise, since Groot is the tree rather than the document; same id/slug/301 scheme) → `bus.emit('groot.saved'|'groot.deleted')` → SSE live-updates the **Pensieve**; audit-log records both. `GET /groot/api/:slug` serves the stored bytes as `application/yaml; charset=utf-8` (RFC 9512), CORS `*`, outside `/api/`, stale slugs 301, `?download=1` → attachment. **The server never parses YAML** — the Edda contract, not Runestone's: alias expansion is a billion-laughs amplifier, so the byte cap does not bound a parse, and the endpoint promises the bytes that were saved rather than "valid YAML". Every parse happens in the browser under `maxAliasCount`, in **`client/src/core/yaml/`** (`analyzeYaml` — one parse feeding issues, documents, advisories and stats; `formatYaml`/`toFlow`/`toBlock`; `yamlToJson`/`jsonToYaml`). Parsing is pinned to the YAML 1.2 core schema with **duplicate keys downgraded to an advisory** (a duplicate is valid YAML everywhere, so an error would refuse the save) and **`<<` merge keys resolved** (what Compose and CI runners do, so the tree matches the reader's tool). The **advisory rail** is the feature's centre of gravity: the Norway problem, duplicate keys, tabs in indentation, version-like and unsafe-range numbers, anchors, merge keys and parser warnings, all **non-blocking and byte-neutral** — `country: no` is flagged and still saves as written, because quoting it for the author changes the document for the reader who wanted a boolean. **Formatting parses with `intAsBigInt` and analysis does not**, which is the one asymmetry worth knowing: re-emitting goes through the parsed value, so without it `buildId: 9007199254740993` formats to `…992`; `toJS` keeps numbers because `JSON.stringify` throws on a BigInt and losing digits in a *JSON conversion* is what JSON does anyway.

- **Atlas (XML) save + the plist table:** editor `POST/PUT /api/atlas` → usecase validates only the `ATLAS_MAX_DOC_KB` cap → `atlas_docs` table (the `groot_docs`/`accio_links` precedent; same id/slug/301 scheme) → `bus.emit('atlas.saved'|'atlas.deleted')` → SSE live-updates the **Pensieve**; audit-log records both. `GET /atlas/api/:slug` serves the stored bytes as `application/xml; charset=utf-8`, CORS `*`, outside `/api/`, stale slugs 301, `?download=1` → attachment. **The server never parses XML and knows nothing about plists** — the Groot contract: entity expansion is an amplifier, so the byte cap does not bound a parse, and the thing that *does* bound it in the browser is the platform's own guard, which a Node process running no browser engine has. Whether a document is a property list is therefore decided in the browser on every load by looking at the bytes — no column, no server-side sniff, and one content type for every document.

  Everything else is **`client/src/core/xml/`**. `analyzeXml` is one parse feeding issues, spans, advisories, the plist tree and stats; `formatXml`/`minifyXml` re-emit from the DOM (`formatXml` keeps the prologue from the *source*, because `XMLSerializer` drops the XML declaration outright, and leaves the root value flush against `<plist>` the way Apple writes it). **No plist library, for the reason `js-yaml` was refused for Groot**: every general-purpose one parses to native JS values, where `<integer>` and `<real>` are both a `number` and `<string>` and `<data>` are the same string once decoded — the declared type is the whole feature. `DOMParser` reports no offsets and the surgical-edit promise is a promise about *bytes*, so a small element-span scanner runs beside it and is zipped onto the DOM in document order, with a **count-mismatch guard**: an internal entity whose replacement text contains markup is the one way the two can disagree, and rather than pair them up wrongly the map comes back empty and the document falls back to code-pane-only.

  **The entity-expansion question was settled by spike, and came back the opposite way to the plan's premise** (the PLAN-20 pattern): a real Chromium *does* expand internal general entities, but libxml2's own amplification guard refuses a nine-level billion-laughs bomb and a 100 MB quadratic blowup in ~10ms, and external entities are never resolved. So there is no `maxAliasCount` equivalent to build — a second limit would be one nobody can tune. What the same spike did surface is that **error detection is easy to get wrong**: the bomb's `parsererror` is grafted *under* a root that parsed fine (so `documentElement` looks healthy), and a valid document may contain an element genuinely named `parsererror` — both are handled by namespace, and pinned.

  The **table** (`core/ui/PlistTable`) is the plist special case, never a mode a person picks: the code pane is always there and the table appears when the root is `<plist>`. It hands the page an **edit intent**, not a computed replacement — it renders from the debounced analysis, so its offsets can be a few hundred milliseconds old, and the page re-parses the live buffer and re-finds the node by path before computing the change. Every edit lands as a real CodeMirror transaction through `JsonEditorHandle.replaceRange`, so **table edits and typed edits share one undo history** and there is no second source of truth. Value edits replace only that value's span; a type change has no "rename this element" DOM operation behind it, so it rewrites that element's own tags and nothing outside them; a reorder rewrites only the span between the two entries involved, re-emitting each from its own source slice so every moved node stays byte-identical and a comment between entries keeps its position. Advisories are three, honestly — duplicate `<key>`, a `<date>` outside Apple's `YYYY-MM-DDTHH:MM:SSZ`, and `<data>` that is not base64 — because XML's grammar makes most of what YAML flags a hard parse error instead. Layout is **Edda's split**, extracted to `core/ui/useSplitPanel` at its second consumer.

- **Accio save + title enrichment:** shelf `POST /api/accio` → usecase validates and normalizes the URL (pure `modules/accio/url.ts`; **any scheme is a link** — `chrome://`, `about:`, `mailto:`, deeplinks — and only the ones that execute or embed inside a page are 422'd: `javascript:`, `data:`, `vbscript:`, `blob:`, `filesystem:`, since a stored row is rendered as an `href`) → `accio_links` table (6-char id, no slug — a link is never addressed by URL, the shelf is its only surface; `tags` is a JSON array) → `bus.emit('accio.saved')` → SSE, and audit-log records it. **The 201 never waits on the network.** The module (not the usecase) subscribes to `accio.saved` and, when the row has no title **and is an http(s) URL** (nothing else has a page to read), runs a detached best-effort lookup: `HttpTitleFetcher` GETs the page with a per-attempt timeout and a hard read cap (`ACCIO_TITLE_TIMEOUT_MS` / `ACCIO_TITLE_MAX_BYTES`), one retry, non-HTML and 4xx/5xx answered as "no title"; a hit patches the row and emits `accio.updated` → SSE, so open shelves fill the title in seconds. A user edit or delete during the flight wins — enrichment re-reads before writing. Shutdown awaits in-flight lookups. The client keeps the shelf live from these three events and filters/sorts locally (see decisions).

- **Nimbus (LAN speed test):** the measurement is split across both sides on purpose — the server moves bytes, the **client owns the clock**, because the number a person cares about is the one their own device sees. `GET /api/nimbus/ping` is a bodyless 204 (the client takes the median of ten, never the mean — one Wi-Fi retry would poison an average). `GET /api/nimbus/down?mb=` streams a window onto one pre-generated random pool (`services/payload-pool.ts`, 4 MiB, cycled by `chunkFrom`), pushed one chunk per `_read` so socket backpressure — not memory — paces it, with `content-encoding: identity` + `no-store` (a compressor anywhere on the path would invent throughput out of a repeating payload). `POST /api/nimbus/up` takes the **raw request stream in a custom `application/octet-stream` parser that counts and discards**: no file, no buffer, so "writes nothing to disk" is true by construction; over `NIMBUS_MAX_TEST_MB` it answers 413 from an `onRequest` hook, before reading a byte. A **single-flight `TestGuard`** (pure, clock-injected) holds a lease per device key across a test's several requests and frees it a grace period after the last one, so a second device gets 409 "another broom is flying" instead of two corrupted readings; `POST /api/nimbus/release` gives the lease back at once (the cancel path), and ping is deliberately ungated so a busy bridge stays reachable. Only a **complete** test is saved: `POST /api/nimbus/results` → `nimbus_results` (device-grouped history, pruned on the audit retention policy) → `bus.emit('nimbus.completed')` → SSE + audit.

- **Logging (server + browser, one archive):** every line is pino JSON in `storage/logs/app.N.log` (daily / 20 MB rotation, `LOG_RETENTION_FILES` kept, `current.log` symlinked at the active one). `LOG_LEVEL` defaults to **`trace`**: since PLAN-16a there is no in-app viewer, so the file is a pure archive feeding Loki and the level is a *query-time* filter rather than a write-time decision that discards data permanently. The level is written as text under **`logLevel`** — Grafana filters `{logLevel="error"}`, not `{level="50"}` — while pino's numeric `level` is deliberately kept beside it, because `pino.transport()` with more than one target runs a worker that re-parses each line to route it and keys on that number (dropping it made the file *and* dev stdout go silently empty); Alloy promotes only `logLevel`, so the pair never reaches Loki; Alloy fills `logLevel` in from the number for files written before the change, so one query spans the whole archive without rewriting it. **Browser lines join the same stream**: the client batches `warn`+ reports to `POST /api/client-logs` (rate-limited, size-capped, unauthenticated by design — it must work when the page is broken), and the `client-logs` module re-emits them through pino with `source: "client"` and the reporting **feature** as `module`, so `{module="accio"}` returns both halves of a feature. `source` is a *child* binding on both sides, never `base`: pino appends to `base`, so binding it there and rebinding on a child emits the key twice, and the two loggers are therefore siblings of a source-free root (`moduleLogger` / `clientLogger`).

- **Metrics & tracing (PLAN-16b):** the durable runtime record is a **snapshot log line** — `module:"metrics"`, one per `METRICS_SNAPSHOT_INTERVAL_SEC`, carrying CPU %, RSS/heap, event-loop lag p50/p99 (reset each interval), SSE clients, `uploadsDelta` and `diskMb`. It is a log line on purpose: Alloy's backfill is a property of *tailing files*, whereas Prometheus **scrapes** (down = the data never existed) and Tempo is **pushed to** (down = buffer, retry, drop), so anything living only in a container cannot explain a hang that happened while the container was off. Counts are **deltas, never cumulative** — they sum over any window in LogQL and survive a restart that would zero a counter. `diskMb` rides a **separate slow timer** because the walk is synchronous: sampling it per snapshot would block the loop per snapshot and record the spike it caused. The module logs through a **`trace`-pinned child**, so raising `LOG_LEVEL` cannot silently stop the record — `METRICS_ENABLED` is the one off-switch. `GET /metrics` (unauthenticated; Prometheus has no session) exposes the same numbers plus a `bifrost_http_request_duration_seconds{route,method,status}` histogram, fed by a **`http.requestCompleted` bus event emitted from `core/http`** — a Fastify hook only sees its own encapsulation context, and every module has its own, so the bus is the only way one module can measure the whole app. Tracing (`OTEL_ENABLED`, default **false**) is loaded with `node --import server/dist/otel.js`, because ESM hoisting means an SDK started from application code instruments nothing, silently.

- **Brotli (PLAN-25 — compress, decompress, and two hand-offs):** `POST /api/brotli/compress?quality=fast|balanced|best` and `POST /api/brotli/decompress` both read `request.raw` through a pass-through `application/octet-stream` parser and pipe it into `zlib`, so neither body is ever buffered — Nimbus's upload-sink posture, applied in both directions. The codec lives on the server because the browsers' Compression Streams API has **no Brotli format** (gzip/deflate only); Node's `zlib` is the same reference `libbrotli` every browser decoder and the standalone CLI use, so output is universally readable, and **large-window mode is deliberately never enabled** so it stays that way. Only `NodeBrotliCodec` imports zlib: the usecases take a `BrotliCodec` interface and the routes never see it. Two caps, both **streaming counters** rather than pre-checks, because neither size is knowable up front — a chunked request declares no length, and a compressed size says nothing about what it expands to. `BROTLI_MAX_OUTPUT_MB` is the **decompression-bomb guard**, and is the first limit in this codebase on bytes the server *manufactures* rather than bytes a client sent; it destroys the pipeline the instant it would be passed rather than draining (there is no sibling upload to protect here). Memory is bounded unconditionally; a **clean status is not**, and that is stated rather than promised: the route holds the response until the first output byte exists, so a failure before then is a clean `413`/`422 INVALID_BROTLI`, and a failure after it — a truncated `.br`, or a bomb whose expansion crosses the cap after real bytes have gone out — ends the connection and is logged. Neither route sets `Content-Disposition`: the client already holds the bytes and names every download itself.

- **Brotli's two hand-offs (both client-side, no module imports another):** *outbound*, Runestone/Edda/Groot/Atlas/Loki each seed `core/brotliSeed.ts` and navigate to `/brotli`, which reads it once on mount and **compresses immediately** (Loki→Variant's immediacy, not Groot→Runestone's pre-fill-and-wait). Pensieve and Variant get no button by design — a listing has no one buffer and a two-pane comparison has two; Loki, which also has two, sends the **output**. *Inbound*, a decompressed result is checked for text on a **bounded 4 KB prefix** (never the whole blob), and below one 8 MB threshold governing display *and* detection alike, `core/contentFormat/` runs real structural tests — JSON must have a container root, XML reuses PLAN-23's namespace-scoped `parsererror` check, YAML must resolve to a mapping or sequence, Markdown needs two distinct constructs — and offers "Open in `<tool>`" through that tool's own session seed. Order is rigid → fuzzy, first match wins, which settles both known overlaps toward the entry with a real parser behind it: JSON is valid YAML, and so is a Markdown document that is only a heading and a bullet list. No match means **no button** — there is no always-true fallback. The gzip comparison beside the Brotli figure is computed **in the browser** with `CompressionStream` (which does support gzip), in parallel with the server call and contained so that losing the comparison never loses the result.

- **Portkey (LAN go-links):** management `POST /api/portkey {slug,url,note?}` → usecase validates the slug (lowercase kebab `[a-z0-9-]{1,32}`, not a `core/reserved-roots` word → 422) and normalizes the target (http(s) only, any host → 422), 409s a taken slug → `portkeys` table (the **slug is the primary key**, immutable — a rename is delete+recreate) → `bus.emit('portkey.saved')` → SSE + audit. The redirect is **`GET /go/:slug`, registered outside `/api/`** so a real route wins over the SPA fallback and `bifrost.local/go/router` is the whole address: it resolves the slug and answers a **302 (never 301) with `cache-control: no-store`** (targets like router IPs move; a 301 would pin the stale one in caches). The **hit count is bumped out of band** — the route schedules the write with `setImmediate` *after* the redirect is flushed (guarded against shutdown; a failed write is a `warn`, never a failed hop), then a dedicated **`portkey.hit` → SSE** (deliberately **not** audited) updates open management pages' hit/last-used within a heartbeat. An unknown slug **302-bounces to `/portkey?go=<slug>`** — the creative-404 pattern, so the management page's "enchant it now" form arrives pre-filled. Each link carries a QR (shared `<QrCard>`) encoding `<origin>/go/<slug>`, so a phone scan lands through the redirect. **Local profile only, permanently** — a go-links service reachable from the internet is an open-redirect/phishing primitive.

## Restart safety (server is stopped/started constantly)

- SQLite in **WAL mode**, `synchronous=NORMAL`, `busy_timeout` set; better-sqlite3 is synchronous so no half-finished async writes.
- Graceful shutdown on SIGINT/SIGTERM: stop accepting → drain/abort in-flight uploads → close chokidar, SSE, DB checkpoint → exit.
- Aborted uploads leave junk only in `storage/tmp/` — swept on boot.
- Boot reconciliation: chokidar initial scan rebuilds the download listing; audit tables reconciled against the folder.
- Drizzle migrations are idempotent and tracked in-DB.
- Proven by `npm run test:resilience` (50 restarts + SIGKILL mid-write / mid-migration + tmp-sweep, all `integrity_check`ed).

## Storage layout

`storage/{uploads,downloads,tmp,data,logs}` inside the repo, gitignored (`.gitkeep` committed). Paths configurable via `.env`. `storage/data/app.db` is the SQLite file. `themes/` (user themes) is state outside `storage/`, so backups cover both.

## Operations & running (PLAN-09)

- **Production entry is `server/src/bootstrap.ts`**, not `app.ts`. `app.ts` self-starts only when it is the *direct* entry (`import.meta.url === argv[1]`); PM2's fork mode wraps the script so that guard never fires. `bootstrap.ts` calls `main()` unconditionally; `npm start`, PM2, launchd, and Docker all point at it. (`app.ts` keeps the guard so tests / the resilience suite can spawn it directly.)
- **Run modes:** macOS runs **native** (PM2 or launchd — mDNS + FSEvents need it) via `ecosystem.config.cjs` / a launchd plist, with one-command `scripts/start-*.sh`. **Docker targets a future Linux host** (`--network host`); it is deliberately not the macOS run mode.
- **Backup/restore:** `npm run backup` / `restore` wrap `core/backup` (online-safe snapshot, rotation, `--include-env` opt-in; restore refuses a live server).
- **Observability (optional, detachable):** `docker-compose.observability.yml` runs Grafana + Loki + Alloy; Alloy tails `storage/logs/*.log`, so it works with any run mode and backfills after downtime.
- **Releases are automated:** `.github/workflows/release.yml` on push to `main` computes the semver bump from conventional commits, tags, publishes a GitHub Release + tarball, and back-merges to `develop` (needs a `RELEASE_TOKEN` PAT).
