# Verify — Bifrost quality gate

Run these in order; stop at the first failure and report it with the failing output. Never raise a PR with any step red.

1. `npm audit` — must report **0 vulnerabilities** at every severity. CI's "Audit dependencies" step fails the PR otherwise. A finding is fixed before anything else, smallest fix first; see `.agents/rules/coding.md`, "Dependencies".
2. `npm run lint` — includes eslint-plugin-boundaries; a cross-module import is a failure, not a warning.
3. `npm run typecheck` — **all five workspaces** (server, client, cli, e2e, web). This is the step that catches what `npm test` cannot: **vitest does not typecheck**, so a green suite is never evidence the workspace compiles (hit for real in PLAN-25 and again in PLAN-27).
4. `npm test` — server + client + cli + web suites, plus the e2e workspace's unit tests of its own support code. The web host's `host.test.ts` puts it in front of a stand-in API on real sockets (PLAN-36): forwarding, SSE, early answers to uploads, client aborts, the 502. The CLI's `*.int.test.ts` files spawn a **real** API per suite via `tsx` (in `BIFROST_RUN=api` on the port they poll), so a failure there can be the server's rather than the CLI's; read which suite failed before assuming. Server tests run the response contract guard in `strict` mode, so a `CONTRACT_VIOLATION` names a route whose schema changed its bytes. A failing `openapi.test.ts` means `server/openapi.json` is stale: run `npm run api:spec` and commit the result (PLAN-32b).
5. `npm run build` — both clients, the API server and the web host (`web/dist`), then `scripts/cli-sync.ts` (builds `cli/`, and re-installs the global `bifrost` unless `CI` is set). A build failure attributed to "the CLI sync" is usually just `cli/`'s own `tsc`. Then `npm run build:standalone` (PLAN-35): the standalone site into `client/dist-standalone/`, whose postbuild step (`scripts/check-standalone.ts`) fails if any `/api/`, `EventSource` or `/go/` survived in the bundle — a hub request that was not wrapped in `__HUB__ ? … : hubOnly(…)`.
6. `npm run test:e2e` (steps 1–6 in one go: `npm run test:all`, which runs both builds) — the end-to-end safety net (PLAN-32a) against the build from step 4, every suite through the web host with the API behind it, as `npm start` runs them (PLAN-36): the installed-CLI suite, the black-box API suite (PLAN-33: contract, fuzz, security, and PLAN-36's run-mode smoke test, then a coverage report that fails if any operation never succeeded; a fuzz failure prints `FUZZ_SEED`/`FUZZ_OP`/`FUZZ_PATH` to replay it), then every browser journey in Chromium desktop, Chromium mobile and WebKit, plus the `standalone` project against `dist-standalone/` (no server at all; any request for something other than a file of the build fails the test). Needs Playwright's browsers once per version (`cd e2e && npx playwright install chromium webkit`). A failure is a client break caught before merge, never a flake to re-run: read the trace (`npx playwright show-trace e2e/test-results/<test>/trace.zip`) and the attached server output. Where a failure is a *known* bug pinned with `test.fail`, the pin flipping red means the bug was fixed — remove the pin. Full detail: `docs/testing.md`.

7. **Restart smoke** (only if the change touches server/storage/DB): `npm start` (both processes), hit `http://localhost:<PORT>/api/health` (through the web host), SIGINT it (the web host stops, then the API), start again, hit it again, then run `PRAGMA integrity_check` against `storage/data/app.db` — expect `ok`. For a deeper pass on storage-critical changes, run `npm run test:resilience` (50 restarts + SIGKILL mid-write/mid-migration + tmp-sweep, all integrity-checked); it is on-demand, not part of `npm test`. Likewise `npm run test:load` (PLAN-34, [`docs/performance.md`](../../../docs/performance.md)) measures throughput, latency and memory under load: on demand before a release or a performance-sensitive change, never a verify step or a CI gate.

8. **Docker touched?** (`docker/`, `compose/`, `docker-compose.yml`, PLAN-39): run the compose combinations CI validates (`.github/workflows/ci.yml`'s *Validate compose combinations*: `cp .env.example .env` first, and remove it after). For the standalone image, `docker build -f docker/standalone.Dockerfile -t bifrost-standalone:ci .` then `scripts/standalone-smoke.sh bifrost-standalone:ci`, which CI also runs. The API image needs `apt`, so a sandbox that blocks it leaves that build to CI. Behind an HTTPS proxy on loopback the build needs `--network host`, the proxy as build args, and its CA trusted by npm.

9. **CLI touched?** If the change is in `cli/`, the browser half of `live-verify` proves nothing — verify the **globally installed** `bifrost` against the built server instead (`npm run build` installs it), and check both a TTY and a piped run: colour, symbols and progress bars must vanish when stdout/stderr is not a terminal, and `--json` must stay parseable through `jq`.

Report format: one line per step (✅/❌), then details only for failures. If a plan file defines extra acceptance criteria for the work in progress, list which ones are covered by tests vs. still manual.
