# New Plan — draft a Bifrost PLAN-XX file

Two plans drafted the same day both needed a second pass to catch real defects — a layering violation, a self-contradiction, an interface snippet that didn't match its own task list, an unresolved edge case, an overstated guarantee. All were catchable on the first pass. This skill exists so they are: read before drafting, then a named checklist before calling anything done.

## 1. Read before drafting

Same order CLAUDE.md already mandates, applied specifically to plan-authoring: `.agent/context/architecture.md`, `.agent/rules/coding.md`, `.agent/rules/git.md`, the recent tail of `.agent/memory/progress.md` and `.agent/memory/decisions.md`. Then **read 2–3 actual recent plan files** (`.agent/plans/completed/PLAN-2[0-3]*.md` is a good default set) as live templates — not from memory of "the format." The format has drifted over the project's history (see §2); working from a stale mental model is exactly how a plan ends up citing a section nobody else uses.

**The plan number is mechanical, not a guess**: it's one more than the highest `PLAN-N` row already in `.agent/plans/README.md`'s gate table (check the table itself, not just the newest file in `completed/` — a plan can be drafted, gated, and sitting un-implemented, which is exactly PLAN-24 and PLAN-25's state at the time this skill was written). The gate is "PLAN-(N-1) merged" worded the way the existing rows word it, even when that prior plan hasn't actually merged yet at drafting time — every plan in this project's history was gated on paper before the thing it depended on was necessarily done.

## 2. The real section order — `plans/README.md`'s own format line is stale

README.md states the format as *"goal → scope in/out → decisions & reasoning → task checklist → touched files → API contracts → acceptance criteria → test checklist."* Every one of the 24 plans in `completed/` was read to check this, and none of them match it: there has never been a "Touched files" section — the task checklist itemizes file paths directly, always — and API contracts come **before** the task checklist, not after. Flag this to the owner rather than perpetuate it; don't fix README.md yourself.

The order actually used, consistently, from PLAN-00 through PLAN-25:

1. `# PLAN-XX — Title`
2. `## Goal` — one paragraph. What ships and why, no task list yet.
3. `## Name` — **only** when the name itself needs a real justification (a pun, a reused existing name, a correction of a name already half-used in the UI — PLAN-19 Groot, PLAN-21 Pensieve are the two real examples). Otherwise the naming rationale is one clause inside Goal; don't manufacture a section for it.
4. `## Gate` — standard from PLAN-08 onward, and near-universal once it starts: every plan from PLAN-08 through PLAN-23 has one **except PLAN-09**, including the simplest single-PR plans (PLAN-13, for instance, is as plain as a plan gets and still has one). One line ("PLAN-N merged. Single PR.") is enough for a simple plan; a multi-part plan gets a PR/branch table and an explicit exception note (PLAN-16, PLAN-17, PLAN-18's shape); a plan with a hard owner-approval checkpoint names it explicitly (PLAN-01's "Approval gate protocol," PLAN-17a's "⛔ HARD GATE"). PLAN-00's special direct-to-`main` rules and PLAN-07's "Execution order" are the same slot under a name that fits what's actually special about that plan. **PLAN-09 is the one real exception, not a pattern to follow** — include this section by default; there is no genuine "skip it" convention to lean on.
5. **Optional: an explicit "verified against the codebase" section right after Gate** (PLAN-12's "Entry points," PLAN-19's "Folding — verified, not assumed"). Worth adding whenever the plan's shape depends on specific integration points in code that already exists — nav wiring, an existing component's exact prop shape, a library's actual folding/parsing behavior. Naming it as its own section makes the verification legible to a reviewer instead of buried inside prose that reads like an assertion.
6. `## Scope` (**In:**/**Out:**) — the default for anything with real scope ambiguity (multiple related backlog items, a feature easily confused with a bigger one). Only PLAN-24 and PLAN-25 actually carry a dedicated section — a long earlier run (18–23) folds scope into Goal plus an inline "Out of scope" Decisions subsection instead, when the boundary was small enough to state in a sentence, and that's still a legitimate choice for a genuinely small boundary. But PLAN-24/25 both needed the dedicated section precisely because they had real scope ambiguity (a backlog item easily confused with a bigger one, several related-but-excluded features) — when that's true, a section a reader can find by its own heading beats a sentence buried in Goal. Default to including it whenever the boundary needs real explaining; fold it into Goal only when one sentence is genuinely enough.
7. `## Decisions & reasoning` — always present, the plan's real content. Early, small plans (00–11ish) use a flat bullet list; from roughly PLAN-12 onward, plans use `###` subheadings per named decision, each a short essay with real reasoning, not just a conclusion. Match the `###` style — it's what makes a decision individually citable later (see how often this project's own plans and progress notes reference "PLAN-19's Tabs decision" or "PLAN-23's parsererror finding" by name). A `⚠️` prefix on a paragraph is this project's convention for "read this one carefully, it's a trap" (PLAN-17 uses it six times over a handful of hazards it found; most plans use it zero or once) — use it the same way, for a real trap worth flagging, not as routine emphasis.
8. `## API contracts` — a table (`| Method & path | Purpose | Notes |`, the Notes column optional for simple contracts) whenever the plan adds or changes routes. For a genuinely pure-client plan with zero server surface, PLAN-18 states it explicitly ("None. The `toolbox` module registers no routes; every tool is pure client compute.") rather than omitting the section — that's the stronger pattern, and the one to follow: an explicit "none" reads as a checked box, silent omission reads as an oversight (PLAN-20 omits the section outright, which is the weaker of the two legitimate options for the same situation).
9. `## Task checklist` (`## Tasks` for a short, simple plan — the two headings pair with `## Test checklist`/`## Tests` respectively; pick the pair that matches the plan's size, don't mix `Tasks` with `Test checklist`). Every checkbox starts unchecked (`[ ]`); they generally **stay** unchecked even after the plan is archived to `completed/` — most archived plans do, a couple (16, 18) got flipped to `[x]` during implementation. Don't pre-check anything while drafting.
10. `## Acceptance criteria` — numbered, sequentially, from 1. If a mid-draft edit needs to insert a criterion, **renumber the whole list** rather than inserting `9a`/`9b` — ad-hoc suffixes are a drafting artifact, not a style, and step 4 below exists partly to catch them before they ship.
11. `## Test checklist` (or `## Tests`) — grouped by kind where the plan is big enough to warrant it (Unit / Integration / Component / Live-verify / Manual is the common grouping), a flat list where it isn't.
12. **Optional: `## On completion`** — only for a plan promoted from `PLAN-99-future-backlog.md`. States that the backlog row is already gone (rows get deleted from PLAN-99 when a plan is *scheduled*, not when it *finishes* — see PLAN-18/20/21/22/23's identical notes on this) and that archiving this file to `completed/` happens in this plan's own implementation PR.

## 3. Before writing "Decisions & reasoning," read the real code

This is why the *first* pass of a plan's design rarely invents a wrong API — grep and read the actual files being touched, the actual function names, the actual existing ports/services/usecases layering, the actual pattern already established for the nearest analogous problem (a seed/hand-off mechanism, a registry pattern, an env var naming convention). Never write a plausible-sounding function signature or assume a file's shape from its name. This is a different failure mode from what §4 checks — §4 is about catching contradictions and gaps *within* a draft that already reads plausibly; this step is about the draft being grounded in fact in the first place.

**Verify third-party library and browser-API claims empirically when the design depends on them — don't trust documentation or intuition.** This project's own history is the evidence: PLAN-19 unpacked and read the installed `@codemirror/lang-yaml` source rather than assume folding worked, and found the actual `foldNodeProp` shape. PLAN-20 and PLAN-23 both *mandated a spike* before committing to a security design, and **both spikes came back the opposite way from the plan's own premise** — PLAN-20 assumed DOMPurify would strip a `<style>` tag (it didn't, and that had a second-order security consequence the plan's own config had left open); PLAN-23 assumed a browser would need a guard against XML entity bombs (libxml2 already refuses them, so there was nothing to build, but the same spike also revealed error-detection had to be namespace-scoped, which nobody had considered). Getting one of these wrong doesn't fail loudly at review time — it fails after the plan is fully written and implementation has started building on the wrong assumption. When a plan's design leans on "library X behaves like Y," say so explicitly and, if the consequence of being wrong is real (a security control, an interface shape, a performance budget), name a concrete verification step rather than asserting it.

**When a plan's feature touches the CLI too — a web feature that gets a matching `bifrost` command, or a CLI command that has to feed a web page — read `cli/src/core/`'s real files (`client.ts`, `documents.ts`, `browser.ts`, `discover.ts`; PLAN-27 is the required read alongside the usual 2–3 recent plans, not an optional extra) the same way §1 already applies to `client/src/core/`. Design explicitly around the one asymmetry that never goes away: **the CLI process can read the local filesystem freely; a browser page cannot read an arbitrary local path at all without a user gesture through the native file/drag-drop picker — that's a hard security boundary, not a limitation to design around.** A plan that has the CLI hand real file *bytes* to a browser tab (not just a URL to something the server already serves) needs its own transport across that boundary — e.g. a short-lived local HTTP server the CLI hosts, reading straight off disk, that the browser `fetch()`s from — stated as a real mechanism, not glossed as "the CLI opens the browser to the file." Reuse an existing `cli/src/core/` primitive (`resolveKind()`, `openInBrowser()`, `client.ts`'s error-mapping) rather than re-deriving the same thing inside a new command, same as this skill already expects for `client/src/core/`.

## 4. Mandatory self-review — run once a full draft exists, before presenting it as ready

Read the whole draft start to finish and check each of these explicitly. Every one below is a real defect this project's plans have actually shipped with, caught either during this exact review step or, worse, during implementation:

- **Layering-rule violations described in the design.** A usecase touching `fs`/another infra API directly, a route doing non-HTTP work (building an archive, running a codec) instead of receiving a ready stream from a usecase. `coding.md`'s "usecases never touch infrastructure directly, routes stay HTTP-only" rule is exactly what `eslint-plugin-boundaries` enforces in code — enforce it on paper too, before the code exists to fail the lint.
- **Cross-module or cross-feature import violations implied by the design.** "Reuse `file-transfer`'s `dispositionFilename` helper" or "call `features/hermes/api.ts`'s `addClipboard`" both read as reasonable reuse and are both forbidden — modules never import modules, features never import features. If two places genuinely need the same small thing, say explicitly whether it moves to `core/` or gets duplicated (this project has done both, deliberately, at different times — cite the reason).
- **Internal contradictions between sections written in different passes.** A plan grows across several editing passes (an owner follow-up, an added feature, a correction), and it is easy for one paragraph to describe one behavior and a later paragraph — answering a related but different question — to describe an incompatible one. Read every "Decisions & reasoning" subsection against every other one, not just against the task list.
- **A code snippet shown in the doc that doesn't match what's required elsewhere in the same doc.** An interface, type, or config shape gets written once early and then the plan grows a requirement (a parameter, a field) that never gets back-filled into the snippet. Diff every shown signature against every place that calls it.
- **Ambiguous "the current X" language standing in for a real multiple-candidate situation.** "Send the tool's current buffer" reads fine until one of the tools in scope has two buffers (an input and an output pane) and the plan never actually decided which. Check every place a plan refers to "the," "current," or "existing" something against whether the real system actually has exactly one candidate.
- **Overstated guarantees where the actual mechanism can't deliver them uniformly.** A streaming design can't always produce a clean HTTP status code on failure, because it may have already flushed real bytes before the failure is detected — state the guarantee that's actually unconditional (memory safety, e.g.) separately from the one that's conditional (a clean 4xx), rather than promising one thing everywhere.
- **A spike or verification the plan calls for, without stating what happens to the design if it comes back the other way.** Per §3 — a mandated spike is not optional detail. If it can plausibly go either way, the plan should say what changes in each case, not just "we'll verify this."
- **Assumed symmetry between the CLI and the browser that doesn't exist.** The CLI can read any local file, spawn a process, hold a real filesystem handle; a browser page can only ever see what a user explicitly drags in, picks through a native dialog, or fetches from a URL. "The browser opens the path the CLI gives it" skips over a real security boundary, not a small implementation detail — the design has to say explicitly how bytes actually cross from one side to the other.
- **Missing standing-doc updates.** See §5 — check the plan's own task list actually includes them, not just that you did them.
- **Numbering hygiene.** No `9a`/`9b` acceptance criteria or task items from an ad-hoc insertion — renumber cleanly.

## 5. Update standing docs as part of authoring — not implementation

A plan is not "just a file" the moment it's written. In the same session, before considering the plan done:

- Add a gate-table row to `.agent/plans/README.md`, matching the existing rows' phrasing (`PLAN-N merged. Single PR.` or the multi-part shape).
- Log the real design calls in `.agent/memory/decisions.md` — dated, with the actual reasoning (not "decided X," but *why*), one row per distinct call, matching the density and specificity every existing row already has.
- Add a session note to `.agent/memory/progress.md`'s "Recent activity" section (newest first), ending with something like "Nothing implemented — plan only" when that's true. This is the project's own established pattern for every plan-only session (PLAN-18 through 25's planning sessions all do this).

The plan file itself lives at `.agent/plans/PLAN-XX-<slug>.md` — directly under `plans/`, **not** under `completed/`. It only moves to `completed/` as part of its own implementation PR, once real work has landed.

## Boundaries

- Never modify an existing plan file unprompted — CLAUDE.md's own rule.
- Never start implementing while drafting a plan; a plan session's deliverable is the file plus the standing-doc updates in §5, nothing else.
- Never invent a lore name unprompted (naming discussion belongs in plain conversation, not baked silently into the draft) — offer options if asked, default to a literal name if none lands.
